# 모바일 캐릭터 화면: 비교 조사와 재설계 제안

조사일: 2026-10-26
상태: 조사·설계 제안. 게임 화면과 기존 시안은 이번 조사에서 수정하지 않음.

## 조사 범위와 근거
개발사 공식 문서, 개발사가 게시한 앱스토어 설명·스크린샷, 공식 제품 설명을 검토했다. UZU의 플레이 화면·자료 분류 화면과 7Days·Scriptic의 공개 스크린샷을 시각적으로 확인했다. 각 앱을 설치해 전편을 플레이한 조사나 시장 점유율·전환율 분석은 아니다. 아래 적용 권고는 확인된 기능과 우리 게임의 사용 맥락을 비교한 설계 가설이다.

## 결론
우리 게임은 휴대폰으로 혼자 완결하는 스토리 게임보다, 실제 사람들의 역할극·대화·조사를 보조하는 서비스에 가깝다. UZU와 앱 연동 보드게임의 진행 구조를 우선 참고하고, 채팅형 게임에서는 모바일에 맞는 정보 단위와 조작만 가져온다.

‘웹툰 + 채팅’이라는 표현 형식보다 ‘현재 단계에서 지금 할 행동을 알 수 있는가, 역할을 이해하는가, 필요한 기록을 짧게 확인하고 대화로 복귀하는가’를 우선한다.

## 사례별 확인 사항과 적용 판단

### 1. UZU — 직접 비교 우선순위 높음
확인: 기본 페이즈를 역할 텍스트 읽기·토론·조사·추가 정보 등에 사용하고, 읽기 연출·투표와 구분한다. 읽기 화면은 자신의 대사를 구분하며 진행자를 명시할 수 있다. 페이즈 내용을 동기화한 텍스트로 배포해 다시 읽을 수 있다. 텍스트는 그룹화와 캐릭터·페이즈별 배포 조건을 지원한다.
관찰: 공식 이미지에 현재 읽기 장면, 자기 대사 강조, ‘다음’ 버튼, 텍스트·단서 접근이 함께 보인다.
적용 판단: 현재 단계와 할 행동을 항상 표시하고, 진행 중 안내와 재열람 자료를 같은 원본에서 생성한다. 앱 안의 음성방 등 우리에게 필요하지 않은 기능까지 복제하지 않는다.
출처: [기본 페이즈](https://docs.studio.uzu-app.com/basic-features/phase/basic/discussion), [읽기 페이즈](https://docs.studio.uzu-app.com/basic-features/phase/basic/script), [텍스트·그룹·배포 조건](https://docs.studio.uzu-app.com/basic-features/texttab)

### 2. Chronicles of Crime — 대면 플레이 보조 구조 참고
확인: 보드게임·앱·장면 탐색을 결합한 협동 수사 게임이며, 공식 제품 설명은 입문용 튜토리얼을 제공한다고 설명한다.
적용 판단: 우리 게임도 설명문만 제공하기보다 실제 조작 한 번을 경험하게 하는 온보딩을 검토한다. 튜토리얼 카드는 연습용임을 명시하고 실제 단서·조사 횟수에 영향을 주지 않아야 한다. 단서 공유 방식은 우리 게임 규칙을 유지한다.
출처: [공식 제품 설명](https://luckyduckgames.com/global/game/1-chronicles-of-crime)

### 3. Duskwood — 다음 행동을 찾는 단서
확인: 개발사 소개는 이미지·영상·음성메시지를 이용하는 수사 이야기로 설명한다. 공식 FAQ는 게임을 계속하려면 무엇을 해야 하는지에 대해 빨간 점이 다음 행동 위치를 가리킨다고 안내한다.
적용 판단: ‘할 일이 있는 곳’을 보여주는 방식은 유용하지만, 점만으로 의미를 전달하지 않는다. ‘역할을 확인해주세요’, ‘지금 조사할 수 있어요’처럼 행동을 글로 표시한다. 타이핑 대기·별도 퍼즐 등 혼자 하는 게임의 페이싱을 대면 게임에 그대로 넣지 않는다.

### 4. 7Days — 모바일 채팅 장면의 정보 단위
확인: 개발사는 모바일용 채팅 기반 미스터리 어드벤처로 설명하며 선택이 이야기와 관계를 바꾼다고 안내한다. 공개 화면은 발화자·짧은 말풍선·응답 선택·하단 탐색을 보여준다.
적용 판단: 짧은 텍스트와 명확한 발화자, 하단의 실행 위치를 참고한다. 우리 캐릭터북의 ‘다음 읽기’ 버튼이 분기 선택처럼 보이게 만들지 않는다. 이야기의 실제 선택은 참가자 사이 대화에서 일어난다.

적용 판단: 익숙한 화면 구조는 학습 부담을 줄일 가능성이 있다. 그러나 가상 인물과의 채팅이 핵심인 서비스와 개인 역할 설명은 목적이 다르다. 비밀을 알고 있는 대화 상대를 억지로 만들거나 실시간 채팅처럼 기다리게 하지 않는다.

## 이전 시안이 모바일에서 약했던 이유 — 현재 화면에 대한 설계 진단
1. 세 컷과 도입 제목이 여러 화면을 차지하고, 핵심 역할 확인 행동은 아래로 밀린다.
2. 상단의 두 모드, 읽기 네 단계, 빠른 찾기의 네 항목이 중첩되어 사용자가 탐색 구조부터 이해해야 한다.
3. 긴 본문과 큰 여백 아래에 다음 버튼이 있어, 처음 보이는 영역만으로는 다음 행동을 알기 어렵다.
4. 말풍선이 있지만 실제 대화 상대나 응답 결과가 없다. 역할 설명문에 대화의 외형만 더한 부분이 남았다.
5. 종이색·명조체·기록철 표현이 강조되어 모바일 플레이 화면보다 편집 문서의 인상이 강하다.
6. 예시 페이지는 현재 게임 단계와 연결되지 않아 ‘지금 나에게 필요한 것’을 고르지 못한다.

## 권장 방향: 단계에 맞춰 행동을 안내하는 모바일 플레이 화면

### 1. 진입 화면에서 현재 단계와 할 행동 하나를 보여준다
- 역할 확인 단계: ‘지금은 역할을 읽는 시간입니다’ + ‘내 역할 확인하기’.
- 조사 단계: ‘공간의 카드 한 장을 선택하세요’ + ‘조사하기’.
- 회의 단계: ‘확보한 단서를 확인하고 말로 공유하세요’ + ‘내 단서 보기’.
- 투표 단계: ‘의심하는 인물을 선택하세요’ + ‘투표하기’.
- 다른 자료는 언제든 찾을 수 있지만 첫 화면의 주 행동과 같은 비중으로 경쟁시키지 않는다.
- 참가자가 읽고 있는 화면을 강제로 닫지 않고, 진행 단계가 바뀌었음을 안내해 직접 이동하게 한다.

### 2. 역할 안내를 내용 단위로 나눈다
초기 설계 가설은 핵심 안내 6~8개 화면이다. 총 화면 수를 먼저 고정해서 사실을 잘라내지 않는다. 원문을 사실·추측·행동 원칙·발언 예시로 분류하고 반드시 읽어야 할 정보를 지정한 뒤 화면 수를 결정한다.
예시 질문: ‘나는 누구인가?’, ‘피해자와 어떤 사이인가?’, ‘지금 무엇이 두려운가?’, ‘그날 실제로 무엇을 했는가?’, ‘어디까지 사실로 말할 수 있는가?’, ‘첫 자기소개는 어떻게 할까?’
- 한 화면은 한 질문과 그 답에 집중한다.
- 속마음의 짧은 문장과 플레이어가 기억할 사실을 구분한다.
- 필수 단서가 담긴 사실은 접힌 부연 설명 뒤에 숨기지 않는다.
- 하단 실행 버튼 위치를 일정하게 두고 다음에 볼 내용을 이름으로 표시한다.
- 긴 정보는 글자를 줄이기보다 여러 의미 단위로 나누거나 정상적으로 스크롤한다.

### 3. 게임 중에는 역할 참고가 즉시 열리게 한다
하단 내 역할·조사·단서함을 기본 탐색으로 검토한다. 내 역할에서 ‘인물 관계’, ‘내 행적’, ‘질문받았을 때’를 바로 제공한다. ‘처음 읽기/다시 읽기 방식’을 사용자가 매번 선택할 필요가 없게 한다.
인물 관계는 인물명과 나와의 관계, 행적은 시각과 직접 한 일, 답변은 해당 인물이 알고 있는 사실과 가능한 말로 구성한다. 특정 인물을 추궁하라는 추천이나 해답 추론은 제공하지 않는다.

### 4. 시각 체계를 다시 잡는다
- 전체 캐릭터 UI는 단정한 모바일 앱을 기준으로 한다. 시스템 고딕 중심, 본문 16~18px·제목 20~24px를 출발값으로 검토.
- 예시 토큰: 배경 #11151A, 표면 #1D232B, 본문 #F1F3F5, 보조 글 #A6AFB9, 강조 #82B5C5. 이는 최종 색상 확정이 아닌 비교용 제안.
- 터치 영역 최소 48 CSS px와 좌우 여백 16~20px를 목표로 잡고 실제 화면에서 확인.
- 주 실행 버튼은 한 개, 기타 행동은 보조 버튼으로 구분.
- 장식용 라벨·영문·질감·금색 프레임·연속 그라데이션을 줄인다.
- 인물 이미지는 감정을 보조하는 크기로 사용하고 대사 영역을 밀어내지 않게 한다.
- 조사 카드의 앞뒷면·물성은 게임 요소로 유지하면서 주변 앱의 글자·버튼·간격을 통일한다.
- 비밀 보호는 쉽게 접근 가능한 ‘화면 덮기’로 제공. 친절함이 추가 팝업과 강제 클릭의 증가로 이어지지 않게 한다.

### 5. 실제 행동을 익히는 짧은 연습은 별도로 검증한다
처음 한 번 연습용 카드 선택·확대·닫기를 경험시키는 안을 검토한다. 실제 조사가 시작됐다고 오해하거나 시간을 지연시키지 않는지 테스트하고, 효과가 없으면 제외한다.

## 구현 전 검증할 세 화면
1. 첫 입장: 다음에 무엇을 해야 하는가?
2. 한소설 역할 안내 한 장: 피해자와의 관계와 감정을 이해하는가?
3. 회의 중 내 행적 찾기: 19:30 기록을 빠르게 찾고 대화로 복귀하는가?
화면 전체를 다시 만들기 전에 이 세 화면의 흐름과 시각 스타일을 비교한다.

## 사용자 확인 계획 — 아래 수치는 목표이며 검증된 성과가 아님
초보 플레이어 5~8명으로 첫 관찰을 진행한다. 기존 시안과 비교할 때 같은 이야기를 두 번 읽어서 생기는 학습 효과를 피하도록 처음 접하는 사용자 그룹을 나누거나 비교 조건을 통제한다.
- 다음 행동을 도움 없이 5초 안에 찾는가?
- 역할 확인 후 자신의 인물·피해자와의 관계·핵심 행적을 본인 말로 설명하는가?
- 회의 중 필요한 시간대 기록을 10초 안에 찾는가?
- 확정 사실과 추측, 숨길 수 있는 정보와 거짓말 제한을 구분하는가?
- 핵심 정보 누락·권한 밖 비밀 노출은 없는가?
- 기존 진행표의 역할 확인 시간(6분) 안에서 내용을 읽을 수 있는가?
- 플레이 중 화면을 오래 붙잡고 있거나, 안내 때문에 참가자 사이 대화가 끊기지 않는가?
이 목표를 만족한 다음에 네 인물 전체로 확장한다. 상업 게임의 사례가 곧 우리 사용자의 이해도 개선을 증명하는 것은 아니다.
